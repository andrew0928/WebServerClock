# 找出該測的網址與時鐘

把入口網址和你關心的操作交給 agent，例如「請讀 `clock-ping --skill target`，幫我確認這個申請網站按下送件後由哪個 host 受理，以及量到的時間能否代表收件時間」。這份指南可離線閱讀，實際調查才需要連線。

## 找到受理操作的公開 host

1. 開啟使用者提供的頁面，記下重新導向後的完整網址。找到對應的送件按鈕，查看表單的 `method`、`action`，以及按鈕有無 `formaction`。相對網址依頁面的 base URL 解析，保留協定與連接埠。
2. 若 JavaScript 接手送件，從按鈕的事件處理程式追到實際請求。也可從使用者正常操作時已有的瀏覽器 Network 紀錄，查看對應的 Fetch/XHR 或 Document，核對 **Request Method**、**Request URL** 及 **Initiator**。分清登入、驗證、上傳附件與最終建立案件的請求。查詢時只需讀取公開頁面或既有紀錄，無須為了驗證而送件或重播 POST。
3. 回報受理請求的公開 host 與依據，註明是從前端程式推得，或已在正常操作中觀察到。若送件流程必須登入才能看見，可請使用者提供該筆請求的方法、host 和路徑，省略個資、Cookie 與 token。

## 核對 clock-ping 實際量到的時間

將下例的網址換成已確認的受理 host。先取四筆樣本：

```sh
clock-ping https://example.com
```

每次探測都從該 host 的根路徑送出 `HEAD /`，跟隨重新導向，使用最終回應的 `Date`。輸入送件的完整路徑或加上 `-m`，都沿用這項規則。可用 `curl -sSIL https://example.com/` 核對每一跳的狀態、`Location`、`Date` 和快取標頭。

若根路徑轉去其他 host、回應來自快取，或代理產生了 `Date`，要把這些情況寫進結論。`Date` 只有整秒精度；即使 RTT 很短，仍不足以確認毫秒級的開放時間。若頁面本來就使用唯讀的應用程式時間 API，查看正常流程中該 API 的**回應內容**與用途。介面顯示時間、判定開放的時間、資料庫寫入或收件排序的時間，各自需要應用程式邏輯或站方文件佐證。

## 判讀網路與代管資訊

| 想知道什麼 | 如何判斷 |
|---|---|
| 對外網路與 ISP | 記下觀測時間、實際連線 IP 及公開 DNS 的 A、AAAA、CNAME。用 RDAP 查網段登記機構與國別，用公開 BGP 資料核對公告路由的 ASN 和營運者。 |
| CDN 或反向代理 | 綜合服務商公布的 DNS 名稱、IP 範圍與該次回應的 `Via`、`Age`、`X-Cache` 等線索。權威 DNS 業者只描述 DNS 服務；缺少快取標頭時，CDN 狀態仍可能是未知。 |
| Cloud provider、region、自建機房、VM 或 container | 分清公開入口與後端工作負載。雲端 IP 可佐證公開入口使用該業者的網路。後端部署位置與執行方式需要站方架構文件、部署資料或維運方確認。網段登記國別、邊緣節點位置及 `Server: nginx` 各有其意義，單靠這些資料無法定位後端。 |

回覆使用者時，先給**建議量測網址**及其對應的時鐘，再列出受理 host、探測的最終網址、能確認的網路資訊及來源。推論要說明依據，證據不足的欄位填「未知」。
