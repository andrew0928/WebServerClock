# 0001　以兩階段取樣研究 HTTP Date 校正

日期：2026-11-26

狀態：已完成可行性實驗。後續採用的細掃策略見[決策 0002](0002-adaptive-http-date-step.md)。

## 背景

固定每秒取樣會反覆讀到秒內相近的位置。在用戶端與伺服器共用同一時鐘的實驗中，僅改變起跑位置，就讓顯示時差的中位數從 −125 ms 移到 −872 ms。另一組每 1.037 秒取樣的實驗把本機時差區間縮到約 −27 至 +9 ms，說明改變取樣位置值得進一步研究。[Issue #3](https://github.com/andrew0928/WebServerClock/issues/3) · [研究紀錄與量測數據](../research/2026-11-26-http-date-calibration.md)

## 決策

將「先以 100 ms 步長定位跳秒區間，再回到區間內細查」列為下一個校正實驗。以各次請求的實際收發時間與 `Date` 推算時差上下界，用區間寬度評估精度。此方法可直接使用公開網站既有的 `HEAD /` 回應。

## 採用前要回答的問題

在約 20 次請求內，10 ms 步進與二分搜尋各能達到多窄的區間？當網路延遲增加時，區間是否仍涵蓋已知真值？待對照實驗完成，再決定細查策略、請求預算以及是否調整 CLI 的取樣與顯示方式。

## 第一輪實驗後的建議

若後續採用兩階段校正，優先考慮二分細查。在 27 組即時產生標頭的條件中，二分法有 17 組達到 ±10 ms，10 ms 步進有 10 組。建議以區間寬度或請求預算作為停止條件，並保留最終區間。不對稱延遲可能讓 20 筆仍不足以達標；固定延後產生的時間值則可能讓區間很窄，卻偏離主機時鐘。產品模式與預設行為留待維護者依結果決定。[實驗數據與限制](../research/2026-11-26-http-date-results.md)
