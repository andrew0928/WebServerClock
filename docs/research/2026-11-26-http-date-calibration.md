# 用 HTTP Date 的跳秒時刻估計網站時差

2026-11-26 · clock-ping 0.1.0 · [Issue #3](https://github.com/andrew0928/WebServerClock/issues/3) · [決策紀錄 0001](../decision/0001-http-date-calibration.md) · [兩階段實測結果](2026-11-26-http-date-results.md)

## 固定一秒取樣的偏差

目前 `clock-ping` 每秒送一次 `HEAD /`，用回應的 `Date` 減去本機請求往返的中點時間。假設兩端時鐘同步，網站在每秒的第 625 ms 產生標頭並捨去小數，單筆讀值就會接近 −625 ms。下一筆又落在相近的位置，五秒平均也會保留這個偏差。[取樣與時差計算](../../src/probe.rs) · [監看模式的統計](../../src/monitor.rs)

實測使用 Homebrew 版 `clock-ping 0.1.0`。本機 HTTP 伺服器與用戶端共用系統時鐘，每次請求即時產生向下取整的 `Date`，已知時差為 0 ms。四個程序的預定啟動時間依序錯開 250 ms。下表為各程序四筆讀值的中位數，單位為 ms。

| 整秒後預定啟動時間 | 本機對照 | www.google.com | assembly.gov.taipei |
|---:|---:|---:|---:|
| 100 ms | −125 | −131 | −131 |
| 350 ms | −373 | −380 | −376 |
| 600 ms | −624 | −630 | −626 |
| 850 ms | −872 | −877 | −875 |

另一組實驗用獨立腳本每 1.037 秒取樣，共 29 筆。保留往返時間的一半（RTT/2）不超過 12 ms 的樣本，再依下節公式取交集。本機保留 29 筆，區間約為 −27 至 +9 ms，涵蓋真值 0 ms。Google 保留 28 筆，約為 −28 至 +21 ms；臺北市議會保留 26 筆，約為 −25 至 +28 ms。兩個公開站台的時鐘沒有獨立真值可供比對。這組資料可作為兩階段取樣的比較基準。

## 從每筆請求求出上下界

令時差 Δ 為「遠端時間減本機時間」。記下本機送出請求的時刻 S、收到標頭的時刻 R，以及回應中的整秒時間 D。若網站在這次往返期間讀取時鐘並向下取整，讀取當時的遠端時間介於 D（含）與 D + 1 秒（不含）之間。單筆樣本因此給出：

```text
D − R ≤ Δ < D + 1 秒 − S
```

同一輪校正假設時差穩定且標頭來自同一個時鐘。所有樣本的下界取最大值、上界取最小值，即得交集。可用交集的中點作為校正值，半寬表示在這些假設下的誤差範圍。若下界大於或等於上界，這批樣本彼此不一致，應記錄此結果。

HTTP 規格限定 `Date` 只到整秒，並允許在產生訊息的過程中取值。向下取整與即時更新都是上述推算的前提。例如標頭若固定晚 200 ms 才更新，就算精確定位跳秒時刻，仍會帶入這 200 ms 的偏差。[RFC 9110 §5.6.7](https://www.rfc-editor.org/rfc/rfc9110.html#section-5.6.7) · [§6.6.1](https://www.rfc-editor.org/rfc/rfc9110.html#section-6.6.1)

## 待驗證的兩階段取樣

1. **每 1.100 秒粗掃一次。** 每筆在一秒內的預定位置前進 100 ms。以網站快 600 ms 為例，忽略延遲時，本機在 `12:00:00.350` 和 `12:00:01.450` 發出的請求會分別讀到 `12:00:00` 與 `12:00:02`。本機經過 1.1 秒，標頭卻前進兩個整秒，表示網站在本機每秒的 `.350` 到 `.450` 之間跳秒。對應的時差區間寬約 100 ms。
2. **回到粗掃區間，以 10 ms 細掃。** 在後續各秒依序瞄準 `.360`、`.370` 等位置，找出邊界兩側的樣本。若從剛跨過邊界的 `.450` 繼續每隔 1.010 秒發送，會先走到 `.460`，得繞回來才會再遇到邊界。另一個候選方法是二分搜尋：先瞄準 `.400`，再依讀值決定下一筆應落在哪一半。理想情況下，四次二分可將 100 ms 縮到 6.25 ms。
3. **依實際收發時間結算。** 預定位置只用於排程，更新交集一律使用實測 S、R、D。例如要達到中點誤差 ±10 ms，交集寬度須小於或等於 20 ms。可先用每輪 20 次請求作為實驗預算；用完後記下實際區間寬度。

## 如何判斷是否值得採用

用可設定已知時差的本機伺服器（例如 0、+600、−600 ms），改變起跑位置，並加入不同程度的往返延遲和抖動。在相同請求預算下比較 10 ms 細掃、二分細查及固定 1.037 秒取樣。每輪記錄真值是否落在區間內、最後區間寬度、耗時，以及達到 ±10 ms 所需的請求數。另以延後更新的標頭檢查固定偏差的影響。這些結果可用來決定細查策略、停止條件及適用的 CLI 模式。
